# For the AGENTS

This is a WordPress plugin that is served via composer + plugin-update-checker. PHP 8.4, esbuild (`tools/build.mjs`), SCSS, wp-env for local dev, changesets for releases.

## Local development

Local URL: derive dynamically from `pnpm env status --json`

```bash
pnpm env start
pnpm watch          # esbuild watch with live reload
```

## Key commands

```bash
pnpm build                  # production asset build
pnpm format                 # Prettier + PHP Pint
composer analyse            # PHPStan static analysis
pnpm test:pest              # Pest tests in the wp-env test environment
pnpm test:e2e               # Playwright e2e tests (`test:e2e:ui`, `test:e2e:install`)
pnpm test                   # Pest + fresh test env + e2e
pnpm wp …                   # WP-CLI inside wp-env
```

## Code style

- derive from the existing code
- prefix getters with `get`; methods that request data from a remote API may use `fetch`
- names must reflect what code does; if a change alters a class/function's behavior, check its name still fits; propose renames that touch call sites
- use domain terms from `CONTEXT.md` for names, if present
- don't rename untouched code
- keep comments as short as possible
- do not add comments if not really required
- only use languages I know. No python please
- Use `/** */` block comments (not `//`) for anything that's not an "end of the line" comment
- docblocks state _what_ a thing does, never _why_ it does it or why it was built that way (exception: Inline docs like e.g. "using the raw value because..."); no {@see} cross-references at all; skip the docblock entirely if the name is self-explanatory; hard ceiling of 3 lines, shorter preferred.
- also keep changesets as brief as possible
- if a changeset already exists that contains obsolete information, delete it

## Before making changes

- if the change is big, always first propose what you are planning, even if not in plan mode

## After making changes

- Keep inline code comments as short as possible. Be extremely concise and sacrifice grammar for the sake of concision
- Mark issues that are solved by the current edit as `done` (see further down, #issue-tracker and #triage-labels).

### PHP

- Prefer new features available in the PHP version declared in `composer.json`
- Classes in `CamelCase`, methods / functions etc in `snake_case`
- After making changes, run `composer analyse` and `pnpm test:pest`
- write tests where appropriate; keep tests lean
- Keep new code DRY! Propose deduplicating existing code. Ask if unsure.
- Prefer fewer, bigger classes: bundle related functionality in one class/file instead of many small ones. A class doing several related, contained jobs is fine
- Prefer WordPress-native functionality over reimplementing it (e.g. `list_files()` over `glob()`).

## Commits and pull requests

- Keep PR descriptions as brief as possible. The title carries the meaning — most PRs
  here have an empty body or a few bullets at most. No headings, tables or walkthroughs.
- Never mention the agent, assistant or tool that wrote the code, in commit messages or
  PR descriptions. No `Co-Authored-By` trailers, no "Generated with ..." footers.

## Do not touch without explicit request

- `lib/` (bundled verbatim, see `lib/README.md`) and `vendor-prefixed/` (generated by `composer prefix`)
- No commits without explicit request
- do not edit TODO files

## Avoid conflicts with multiple sessions

- every new claude session creates a new branch off main if there are code changes
- when the task is complete, merge back into main after confirmation
- delete branch after merge without asking

## Project structure

| Path | Purpose |
|------|---------|
| `rh-admin-utils.php` | Plugin entry point |
| `src/` | PHP classes (`RH\AdminUtils\` namespace) |
| `assets-src/` | JS + SCSS source, built by esbuild into `assets/` |
| `lib/` | Bundled third-party libraries (plugin-update-checker) |
| `vendor-prefixed/` | Strauss-prefixed dependencies |
| `languages/` | Translations (`pnpm make-pot`) |
| `tools/` | Build, release and wp-env scripts |
| `tests/Pest/` | Pest integration tests |
| `tests/e2e/` | Playwright e2e tests |
| `tests/SetupPlugin/` | Helper plugin loaded into wp-env |

## Agent skills

### Issue tracker

Issues and PRDs live as markdown files under `.scratch/<feature-slug>/`.

### Triage labels

Canonical vocabulary (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`).

Always move `Status: done` issues into `.scratch/done`.
